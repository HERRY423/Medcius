# PHI 覆盖与 CPU 高峰并发改进（2026-11-15）

范围：本地插件工程与人工编写的合成开发样例。保留原模型、量化精度、原文坐标、
生产双轨检查、追加式审计和 `complete_deidentification: NOT_ESTABLISHED`。
此文记录工程实现与实测边界，不是临床模型验证、医院验收或部署批准。

## 改动与解决的问题

1. **补齐已知身份信息的覆盖。** 患者会话词典支持院区、机构与病区的名称/别名，
   encounter 的 serviceProvider / managingOrganization，以及 FHIR 地址 city/district/state。
   医护结构化姓名可生成有界的“姓氏＋职称”变体；复姓、罕见字及补充平面汉字保留
   正确 UTF-16 定位。“老郄”等熟称只使用来源明确提供的 alias，不从任意正文猜测。
   嵌套来源归属冲突会拒绝；新注入的实体会清空先前词典扫描缓存。
2. **修复临床文字误删。** 原来的职称规则会把“主治医师查房”中的“主治”当成人名。
   现在排除明确的职称修饰语；真实会话姓名依旧优先，不能利用药名白名单漏过已知身份。
3. **让不同请求真正并行。** 原来的四个 Worker 是一个请求内的批处理线程；外层
   FIFO 只有一个执行槽。新增 1–4 个独立本地进程，每个进程初始化、核验模型并完成
   单条/批量推理预热，全部成功后才被生产工厂注册。原单进程默认路径仍保留。
4. **把高峰成本和失败显式化。** 一个全局有界队列控制进程池，不给每个进程另开
   32 个待处理槽。超时从入队计算，调用方超时后原生工作仍占槽。子进程退出、异常
   回复或硬停滞使整个池失效，不自动重启、不回退到词典或旧缓存。排队、推理服务、
   超时、拒绝及内存指标均为无患者文本的聚合计数。
5. **实现可失效的病区预热。** `createWardPhiSessionCache` 只准备实体词典，默认
   64 会话、5 分钟 TTL；租户/病区/患者/就诊/会话与来源版本共同约束复用。
   同版本却变更元数据会拒绝；到期、转科、出院、注销可失效；正在使用的词典完成后
   释放。空闲词典定时销毁，不等待下一次请求。此缓存关闭正文扫描缓存，
   不保留病历、脱敏快照或 NER 结果，每次新的临床操作仍执行真实模型。

实现入口：`phi-entity-session.mjs`、`phi-ward-cache.mjs`、`phi-runtime.mjs`、
`runtimes/cn-phi-ner/process-pool.mjs` / `process-worker.mjs`、`inference-queue.mjs`。
具体 API、配置、关闭与回滚说明见运行时 README。

## 并发实验与选择规则

测量对象是 **PHI 入口到患者快照生成**。64 个固定合成来源、长短病程混合，
并发突发量 1 / 8 / 32 / 64，每档 3 轮，测量前 3 个快照预热；每个新请求重新推理。
报告分别列完成请求的延迟、拒绝请求的延迟、拒绝原因、吞吐量、队列等待/服务时间
分布，以及启动耗时和各进程 RSS。进程内预热还包含真实单条与批量模型探针。
最终测量前后核对实现文件摘要，源码变动会拒绝输出最终报告。

默认低线程池（2 进程 × 每进程 1 batch worker × 1 ORT 线程）未显示稳定加速。
第二轮增加相同最大原生线程数的配置（2 × 2 × 2 = 8）作比较；原拓扑最大也是
4 × 2 = 8。该数字只限制本应用同时执行的 ORT 工作，不是 OS CPU 配额，也不能
将本机测试冒充 4 vCPU 机器测试。进程池需要更多独立模型会话，必须检查内存。

冻结源码的最终测量运行于 Windows 10.0.26200 / Node v24.13.0 / Intel Core Ultra 5 225H，
14 个可用逻辑处理器。以下延迟是每档 **三轮完成请求 p95 的平均值**，不是所有请求
混在一起的 p95；拒绝请求没有混入“完成很快”的样本中。

| 同时到达请求数 | 原单队列 p95 均值 | 2 进程低线程池 | 2 进程、8 线程预算 | 原单队列完成 / 拒绝 | 两种进程池各自完成 / 拒绝 |
|---|---:|---:|---:|---:|---:|
| 1 | 237.91 ms | 367.98 ms | 230.50 ms | 3 / 0 | 3 / 0 |
| 8 | 831.88 ms | 681.79 ms | 460.07 ms | 24 / 0 | 24 / 0 |
| 32 | 3353.14 ms | 2718.51 ms | 1782.54 ms | 96 / 0 | 96 / 0 |
| 64 | 3393.34 ms | 2728.93 ms | 2331.73 ms | 99 / 93 | 102 / 90 |

在这个负载与本机上，8 线程预算池的 32 请求档 p95 均值下降 46.84%
（computational × benchmark_measured；合成入口负载）。排队等待的全程平均值
从 670.30 ms 下降到 400.51 ms；两种拓扑均未触发 30 秒超时。64 请求同时到达时
仍明显超出容量：池只有 2 个执行槽 + 32 个等待槽，90/192 个请求明确拒绝，
不能宣称“消除了早高峰拥塞”。吞吐、每轮结果与拒绝延迟见 `peak-final.json`。

8 线程预算池工厂启动耗时 2789.71 ms；两个子进程末次报告的 RSS 合计
2136.87 MiB（约 2.09 GiB），不含父进程，且不是进程峰值。低线程池为 1625.74 MiB。
原单进程本轮未采集 RSS，不能填成零或据此推导内存提升比例。前两轮的低线程池
没有稳定改善；全部结果保存在 `peak-preliminary-1.json` / `peak-preliminary-2.json`。
这些顺序执行的本机测试仍受系统负载和调度影响，不证明其他主机或医院的净收益。

本机测试配置可在不低于 8 个可用逻辑处理器的目标环境进行复核：

```powershell
$env:MEDCIUS_CN_NER_PROCESSES='2'
$env:MEDCIUS_CN_NER_THREADS='2'
$env:MEDCIUS_CN_NER_BATCH_WORKERS='2'
$env:MEDCIUS_CN_NER_CPU_BUDGET='8'
node scripts/verify-runtime.mjs
```

这不是 4 vCPU 配置建议。4 vCPU 前置机必须使用预算不超过 4 的配置另测，
例如 processes=2、threads=1、batchWorkers=2；本轮没有声称已经在该硬件验证。

最终测量数值与验证状态由同目录的验证回执绑定。此负载不等于旧报告的完整查房
流程；原有 80 ms **平均耗时**门槛没有放宽，不能用此处 p95 或入口耗时宣布达标。
截图中的 07:30–08:15 只是用户提供的示例忙时，未作为本院已核实的到达率输入。

## 部署选择与改判条件

- 在目标前置机运行相同 `benchmark-phi-peak.mjs`（本地 CPU，约数分钟，具体依硬件），
  再用院方授权、已脱敏的代表性负载检查等待、完成延迟、拒绝率及 RSS。如果增加进程
  没有改善目标延迟或挤占其他服务资源，保持原单队列配置或减少原生并行度。
- `MEDCIUS_CN_NER_PROCESSES` 显式启用新路径；部署方同时配置 threads、batch workers、
  cpu budget、max pending、timeout。总预算受本机 availableParallelism 限制。
  通过启动预热后再接流量；按病区错峰准备词典，不缓存“之前已脱敏”的病历结果。
  队列满时宿主应展示可重试的暂时不可用，避免无界自动重试或未经检查的正文输出。
  队列限额与 30 秒默认时限作用于一次 NER 调用，不是整次多阶段查房；宿主须通过
  `signal: AbortSignal.timeout(...)` 施加整个入口操作的期限并传递用户取消。
- 上述 24 条开发样例之外的真实 PHI 召回率仍为 NOT_ESTABLISHED。升级这一判断需要
  获准的本地病历与独立实体跨度标注，分别报告未知裸姓名、医护熟称、机构/地名、
  OCR/语音混淆的遗漏，以及临床字段误删。若新覆盖带来不可接受的临床文字损失，
  应收窄该别名来源/规则，而不是宣称模型通过或以全阻断替代有效脱敏。

未更换或训练模型，未外传病历，未把本地源码更新宣布为安装插件的宿主验收。
新路径是可选的本地部署能力；从环境中移除进程池相关配置并重启可回到原拓扑，
PHI 双轨要求和失败阻断不变。
