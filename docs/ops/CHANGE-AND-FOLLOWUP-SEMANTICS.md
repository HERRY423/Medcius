# 变化、到达时间与待复核状态

本契约用于 Medcius 查房前摘要的本地工程、合成回放和受控静默研究。它描述来源记录，不作诊断、治疗建议或自动闭环判断。临床投放仍受独立治理门禁约束；静默接口继续返回空卡片、空草稿和 `summary: null`。

## 三类状态分别表达

| 维度 | 回答的问题 | 不能推断的内容 |
| --- | --- | --- |
| 记录状态 | 来源报告为正式、修订、取消、录入错误、初步或未知状态吗？ | 正式结果不等于医生已经确认；取消不等于已执行或已复核。 |
| 发生与到达时间 | 事件何时发生，何时记录或接收，修订发生在何时？ | 本窗口收到旧记录，不代表本窗口发生新的病情变化。 |
| 来源可用性 | 本次读取成功、有零条结果、失败，还是无法确认完整性？ | 读不到数据不等于没有该项检查；零条结果也不证明临床阴性。 |

`blocks.record_changes.items` 保留来源标识、来源系统、版本、原始状态、变化时间及其依据。`change_type` 与 `arrival_status` 是不同字段：一个修订结果也可以是迟到记录。

历史版本保留在条目中并标明 `superseded`，不计入当前状态数量。`counts.new_result` 只计当前有效版本且独立出具时间在本窗口内的结果；迟到的历史结果不增加本窗口新结果数。不能据此声称相对上一轮摘要首次出现。

| `change_type` | 展示含义 |
| --- | --- |
| `new_result` | 来源标记为正式结果且提供独立出具时间；没有上一快照基线时不声称首次新增，`is_new_since_previous` 保留 `null`。 |
| `revision` | 来源明确修订，或同一资源的后续版本明确改变了结果内容；旧版本的人工确认不能自动覆盖新版本。 |
| `cancellation` | 来源取消或撤销，需要核对；不当作正常结果或已完成。 |
| `entered_in_error` | 来源标记录入错误；不再作为当前有效结果。 |
| `preliminary_result` | 来源为初步结果，不能当作正式结果。 |
| `no_result` | 有医嘱、预约或采集状态，但不能据此推断最终结果。 |
| `unknown` | 状态缺失或无法识别，或正式结果缺少独立出具时间而无法判断新增，保留对应维度未知。 |

同一来源资源的不同版本通过来源系统、资源标识和版本信息关联。版本号按不透明标识处理，不按字符串大小或数组顺序决定新旧。缺少足够时间或明确替代关系时保留冲突，不能选择一个看似合理的版本。不同资源标识下的同一检验项目不自动视为同一资源修订。

## 来源可用性

`blocks.source_availability` 与来源快照使用同一数组，每项包含：

- `connector_id`、`kind`、`status`。
- `fetched_at`、`source_version`。
- `record_count`、`accepted_record_count`。
- `reason_code`：安全错误码或 `null`，不含原始请求、凭据或患者正文。

`available` 表示接口读取成功；`available_empty` 表示读取成功但返回零条；`unavailable` 表示接口读取失败；`unknown` 表示无法确认完整性或记录是否可用。未提供某来源的状态，不得补写为成功、阴性或未检查。

接口状态与临床事件时点不同。接口的 `fetched_at` 不能替代采样、事件发生、记录、修订或人工确认时间。

## 人工确认与闭环

`blocks.high_risk_followup` 将来源结果状态与人工复核、闭环状态分开。结果出具后可以仍待确认；修订后旧确认不自动沿用；取消或录入错误需要核对；来源不可用、时间未知或版本冲突不能显示为已闭环。无法可靠计算到期时间时，`overdue` 保留 `null`，不生成虚假的逾期判断。

本轮不添加治疗处置动作，也不将跟踪状态写回 EHR。

影像开单时间与实际检查时间分别保留；开单时间不能替代检查发生时间。抗菌药物提醒只使用当前明确有效且未结束的医嘱，表达“距医嘱开立时间”，不把它称为实际连续给药天数。已撤销、录入错误、版本冲突的笔记、影像或医嘱不得从其他摘要面板重新进入当前事实。

## 宿主和研究档案的一致性

1. `HospitalAgentAdapter` 将来源可用性传给引擎。来源快照顶层与数据集中的可用性不一致时拒绝执行。
2. 全部版本与时间窗口外的记录进入内部 `recordHistory`，供引擎保留迟到、修订和取消事件；当前数值面板使用经过状态与时间核验的记录。
3. 常规宿主响应只返回经过 PHI 处理的摘要与来源元数据，不携带 `engine_input`、`recordHistory`、原始数据集或注释副本。
4. 研究档案保存同一 `as_of`、规则、来源可用性、完整生命周期输出及内部重放输入。顶层可用性必须与冻结输入和输出一致。
5. 档案写入前验证精确重放，读取时验证完整性。记录、输入、输出的哈希仍受租户隔离及审计锚定保护。运行时或实现身份改变后，不能声称与原实现相同的重放。

已有档案不被覆盖，也不因为新字段而自动升级其证据状态。工程通过、合成验证、医院部署验收和临床证据继续分别报告。

## 验证入口

`tests/test-lifecycle-surface.mjs` 使用纯合成输入覆盖来源可用性、空结果与接口失败的区别、修订/取消/录入错误/未知/迟到记录、模型响应边界及冻结重放。它不构成医院接入或临床有效性证明。

其他回归入口：`test-record-change-semantics.mjs`（摘要与计数）、`test-record-version-edge-cases.mjs`（版本、时间边界与冲突）、`test-followup-lifecycle.mjs`（人工确认与未闭环）、`test-source-lifecycle.mjs`（来源读取）、`test-lifecycle-normalizers.mjs`（影像及医嘱）、`test-lifecycle-draft-boundary.mjs`（渐进视图与草稿）。这些入口均纳入仓库完整检查。
