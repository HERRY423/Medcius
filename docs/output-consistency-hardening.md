# 同一份输出内部一致性加固

## 本轮复现的矛盾

1. 查房适配器在摘要生成后追加 `GAP-SRC`，缺口存在于页面却不在可选条目、计数或证据列表中。
2. 版本解析器已确定同一报告内容发生修订，却同时返回 `change_type=revision` 与 `result_status=final`。会诊视图因此仍显示“最终报告”，交接班和出院又自行改写为“修订”。
3. 查房危急卡片可能缺少当前版本与结果状态；详情显示修订，首屏显示状态未知。不同模块对 `interpretation=critical` 的识别也不一致。
4. 相同时间、相同条目数量、不同内容的查房输出可能具有相同来源封套校验值。
5. 三层视图可以被外部参数重新标为另一个患者或另一时间窗；可变对象及共享引用也可能让已生成的视图局部漂移。

## 实施

- 版本解析器统一输出推导后的修订状态；原始来源状态仍保留供核对。
- 查房资料缺口和护理/影像辅助面板在引擎内生成。适配器不再在计数和证据生成后追加内容。兼容字段从同一组已选择资料派生。
- 危急卡片由选中的当前版本生成，明确资源、系统、版本、状态和采样时间。来源标记不再被描述为插件自行推断出的阈值。
- 会诊、交接班、出院及查房共用输出一致性检查；不一致时拒绝生成/导出。校验覆盖计数、明细、证据、分层投影、交接事件与资料包绑定，以及出院医学判断边界。
- 引擎输出和查房渐进视图为独立的只读副本。后续更新必须重新生成，不能直接修改旧输出。序列化 JSON 的外部副本仍需调用相应校验器，不能把 JavaScript 冻结当作跨进程授权。
- 会诊/出院文本导出重新检查内容摘要；交接文本检查资料包和事件摘要。查房封套摘要新增完整脱敏摘要绑定。
- 外部参数不能把查房摘要改成另一患者或另一时间窗。
- 出院跟进完整性按当前结果的精确来源链接核对，避免同名计划 ID 误借另一条计划的完整性。

## 持续回归

新增 `tests/test-output-consistency.mjs` 并纳入全量检查。包含：跨视图修订一致、显式危急标记、缺口/证据覆盖、同计数不同内容、撤销与乱序重复输入、不可变输出、主动破坏计数/证据/责任/结论、患者与时间窗错配。

这是工程上的结构和状态约束，不是自然语言的全部语义证明，也不证明来源真实、院内覆盖完整、临床正确或节时。需要继续用独立临床标注评估。原临床冻结状态保持。

## 兼容性

旧消费者若直接修改引擎返回对象，需改为复制后编辑或重新生成。推导修订现在统一返回 `revised`；消费者需要区分原始来源状态与解析后的当前状态。查房来源摘要校验值会随内容变化而变化，旧缓存不得跨算法混用。历史归档的精确重放可能因新状态和新增证据字段产生差异，应保留历史输出及原实现版本，不改写历史记录以制造一致。
