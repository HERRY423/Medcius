# Medcius

**住院医生查房前患者变化摘要插件**

Medcius 面向住院医生查房前的病历预阅环节。它读取当前患者在过去 24 或 72 小时内的病历、检验、医嘱和检查状态，将分散信息整理为一屏摘要，帮助医生更快回答四个问题：

1. 发生了什么变化？
2. 今天仍待处理什么？
3. 哪些关键资料不足？
4. 每条信息来自哪里？

当前版本为 **`0.2.0-pilot` 工程试点版**。项目尚未获得真实临床效率、安全性、多中心部署或医疗器械注册证据，不应作为自主诊断、治疗推荐或未经医生确认的病历写回工具。

## 产品边界

### Medcius 做什么

- 接收当前患者和就诊上下文；
- 汇总 24/72 小时内的症状与体征记录；
- 计算检验指标的纵向变化；
- 展示新增、停用和调整的用药医嘱；
- 汇总待回报检查、待执行医嘱和待办会诊；
- 显式提示过敏史、近期肾功能、体重等资料缺口；
- 将输出绑定到病历原文或 FHIR 资源标识；
- 仅根据医生勾选的条目生成病程记录草稿。

### Medcius 不做什么

- 不生成诊断、鉴别诊断或疾病概率；
- 不推荐药物、剂量、检查或治疗方案；
- 不把“未检出”解释为“临床上不存在”；
- 不在缺少患者上下文时补造患者或临床事实；
- 不自主创建或更新 EHR 资源；
- 不把单元测试、合成病例或演示影子研究称为临床证据；
- 不把医保编码、处方审核、临床试验检索或多 Agent 编排纳入旗舰产品。

## 医生看到的内容

| 区块 | 内容 | 输出纪律 |
|---|---|---|
| 发生了什么变化 | 症状/体征、检验趋势、用药变化 | 事实与来源并列展示 |
| 今天仍待处理什么 | 待回报检查、待执行医嘱、待办会诊 | 不推断临床优先级 |
| 哪些资料不足 | 过敏史、肾功能、体重等缺口 | 缺失即缺失，不自动补全 |
| 查看原始证据 | 原文 span、FHIR resource id、时间戳 | 无可靠来源时不伪造 span |

插件的目标不是生成一篇新的长摘要，而是减少医生在多个页面之间寻找变化和待办事项的时间。

## 当前实现

```text
EHR / FHIR / CDS Hooks patient-view
                 │
                 ▼
       患者与就诊上下文解析
                 │
                 ▼
       PatientEvolutionEngine
       ├─ 24/72 小时窗口
       ├─ 检验趋势
       ├─ 用药变化
       ├─ 待办事项
       └─ 资料缺口
                 │
                 ▼
       证据绑定与一屏侧边栏
                 │
                 ▼
       医生选择后的病程草稿
```

主要入口：

- `GET /sidebar`：查房前侧边栏；
- `GET /cds-services`：CDS Hooks 服务发现；
- `POST /cds-services/medcius-patient-evolution`：`patient-view` 服务；
- `GET|POST /api/v1/patient/evolution-summary`：结构化变化摘要；
- `POST /api/v1/patient/progress-note-draft`：根据医生选中条目生成草稿；
- `GET /health`：运行状态与工程门禁摘要。

生产 MCP 清单只启动四个本地 stdio 服务：

- `FHIR`：SMART on FHIR R4 数据读取；
- `documents`：病历附件与文档提取，清单中的历史名称为 `Contracts Analyzer`；
- `PHI Guard`：本地 PHI 扫描与处理；
- `Audit Chain`：本地防篡改检测用哈希链审计。

部分非旗舰运行模块已移入 [`experimental/`](experimental/README.md)。但由于仓库继承自上游通用 healthcare 插件，`plugins/medcius/skills/` 仍包含若干遗留技能；当前发布目录尚未做到物理上的最小化。它们不属于旗舰预期用途，拆分或从生产包排除属于 P0 工作。

## 安全与证据纪律

### 患者上下文

CDS Hooks `patient-view` 路径在缺少有效 Patient ID 时返回资料不足卡片，不生成演示患者。真实医院接入还必须验证患者、就诊、用户与租户绑定，患者错配应作为零容忍事件处理。

### 检验参考范围

检验高低判断优先使用医院 LIS/FHIR `Observation.referenceRange`。缺少参考范围时只展示数值、时间和趋势，不使用通用“专家阈值”代替本院规则。当前危急值逻辑仍需要接入医院正式危急值表后才能用于临床提示。

### 来源与原文

自由文本事实必须携带可在原病历中验证的 span。结构化 FHIR 事实应绑定真实 resource id、版本和时间；没有原文 span 时保持 `null`，不能通过字符串拼接制造证据。

### 数据路径

FHIR 与本地 MCP 服务运行在用户机器或医院环境中，但工具结果可能进入承载插件的模型会话。因此，“本地连接器”不自动等于“数据绝不离院”。真实部署必须明确宿主、模型供应商、日志、遥测、数据处理协议和医院网络边界；需要完全院内处理时，应使用经医院批准的院内部署方案。

### 写回

旗舰工作流按只读设计。FHIR 连接器虽然保留显式授权后的通用创建/更新工具，但它们不属于查房摘要生产流程。病程草稿必须由医生逐项确认；当前代码生成的是草稿，不代表已经完成医院有效电子签名或 EHR 写回。

## 当前成熟度

| 层级 | 当前状态 | 可以说明什么 |
|---|---|---|
| 工程实现 | 已有代码与自动化检查 | API、解析、计算和失败路径具备可测试实现 |
| 合成验证 | 有合成病例和演示评测 | 只能验证软件契约与评测管线 |
| 真实 EHR 接入 | 未完成独立验证 | 尚无生产医院端到端 SMART/FHIR 验收证据 |
| 临床事实准确性 | 未建立 | 尚无真实连续病例的独立医生标注结果 |
| 医生效率 | 未建立 | 尚无 time-motion 或对照工作流证据 |
| 临床安全与泛化 | 未建立 | 尚无真实病区、跨科室或跨医院证据 |
| 监管与商业准入 | 未完成 | 预期用途、分类界定、QMS 和采购材料仍需正式推进 |

任何 `engineering_pass` 或 `synthetic_validation_pass` 都不能升级为 `clinical_evidence_pass`。

## 本地开发与沙箱演示

### 环境

- Windows、macOS 或 Linux；
- 当前 Node.js LTS；FHIR 开发环境建议 Node.js 22.13 或更新版本；
- 真实 FHIR 测试需要医院或沙箱签发的 `FHIR_BASE_URL` 与 `FHIR_CLIENT_ID`。

### 启动开发服务

以下设置只允许本机沙箱演示，不得用于真实患者数据：

```powershell
$env:MEDCIUS_ALLOW_ANONYMOUS = "true"
$env:MEDCIUS_PROFILE = "demo"
node plugins/medcius/servers/api/src/server.mjs
```

打开：

- `http://127.0.0.1:8080/sidebar`
- `http://127.0.0.1:8080/health`
- `http://127.0.0.1:8080/cds-services`

当前 REST 摘要路由仍包含演示数据回退，而且代码尚未把该回退强制限制在 `demo` 配置中，因此只可在隔离沙箱使用。清除该回退并让生产路由从经认证的 EHR 上下文取数，是进入真实静默试点前的 P0 阻断项。

### 安装插件包

Claude Code 开发评估：

```text
/plugin marketplace add HERRY423/Medcius
/plugin install medcius@medcius
```

Codex 本地开发评估：

```powershell
codex plugin marketplace add "$PWD\.agents\plugins"
codex plugin add medcius@medcius-local
```

Codex 入口用于工程审查、合成数据回放和获批沙箱验证；它通过 Codex 专用
manifest 启动只读 FHIR MCP 适配器、documents、PHI Guard 和 Audit Chain，
不构成医院临床部署或合规批准。

仓库同时包含 Agent Plugins 便携清单。此安装方式用于开发者验证，并不构成医院临床部署或合规批准。

### Trae / WorkBuddy 项目协作

仓库同时提供不依赖 Codex manifest 的项目级适配：

- Trae：启用项目级 MCP 后读取 [`.trae/mcp.json`](.trae/mcp.json)，规则位于 [`.trae/rules/project_rules.md`](.trae/rules/project_rules.md)，技能入口位于 [`.trae/skills/`](.trae/skills/)；
- WorkBuddy / CodeBuddy：读取根目录 [`.mcp.json`](.mcp.json)、[`.rules/`](.rules/) 和 [`.codebuddy/skills/`](.codebuddy/skills/)；
- 两类入口都复用 `plugins/medcius/scripts/codex-mcp-server.mjs`，FHIR 工具由启动器强制保持只读。

WorkBuddy Enterprise 仍需在企业后台分别挂载规则、技能与 MCP，并在 Test Run 中验证；本仓库不把 Codex manifest 冒充为企业可安装包。

### 运行检查

```powershell
node scripts/run-all-checks.mjs
```

主检查包含工程测试、合成陷阱和演示影子研究。应查看每一层的独立结果；总命令退出成功不代表获得真实临床证据。

## 从工程试点进化为实用插件

### P0：建立可信的试点基线

进入医院前必须完成：

- 删除生产 REST 路由的演示患者与演示临床数据回退；
- 将权限从遗留的审方命名改为查房摘要专属权限；
- 用医院 IdP/JWKS 或正式 SMART 身份链替代开发 JWT；
- 限制生产 CORS、绑定地址、TLS、日志和租户策略；
- 将 LIS 危急值、本院单位和参考范围作为受控配置；
- 清理仍引用审方、药师、多 Agent 或旧工作台的内部文档和评测；
- 固定一个可重放的 pilot commit，并由托管 CI 验证该精确提交。

退出条件：无演示数据进入生产路径；患者绑定、来源绑定和失败关闭均有自动化负向测试。

### P1：完成一个真实 EHR 的只读集成

选择一个病区和一个医院系统，完成 Patient、Encounter、Observation、MedicationRequest、AllergyIntolerance、DiagnosticReport、ServiceRequest 与 DocumentReference 的字段映射。

重点不是“支持所有 FHIR”，而是证明：

- 医生无需再次选择患者；
- 数据时间、单位、状态和版本可解释；
- 页面切换后患者上下文不会串位；
- 部分资源不可用时明确降级；
- 不请求查房摘要不需要的权限。

退出条件：医院沙箱中的端到端只读验收通过，并形成可复用的字段映射和故障清单。

### P2：真实连续病例静默验证

插件在真实数据上运行但不向医生展示。由两名住院医生独立标注“应出现的变化、待办和资料缺口”，第三人处理分歧。版本、病例纳入规则、主要终点和分析计划应预先冻结。

至少报告：

- 患者错配数；
- 虚构事实数；
- 关键事实遗漏率及置信区间；
- 来源绑定覆盖率；
- 无法解析和弃权率；
- P50/P95 延迟与系统失败率；
- 不同病种、住院阶段和数据完整度下的分层表现。

退出条件不应只写“准确率达标”，而应由医院临床负责人预先批准严重遗漏定义和可接受上限。

### P3：医生可见的人因与效率试点

在冻结版本上比较同一医生“常规预阅”和“插件辅助预阅”。北极星指标为：

> 每名医生每班经过验证的节省分钟数，同时关键事实遗漏不劣于原工作流。

主要观察：

- 每位患者的预阅时间；
- 点击数和页面切换数；
- 摘要打开、完成和主动关闭率；
- 医生删除、修改和补充比例；
- 回看原始证据的比例；
- 关键遗漏、错误事实和认知负担；
- 插件不可用时能否安全回到原工作流。

退出条件：效率改善具有实际意义，安全终点满足预设非劣效边界，且医生愿意在无强制要求时持续使用。

### P4：第二医院复制与运营化

第二家医院应使用不同 EHR 或不同科室。只允许新增适配器和医院配置，不能复制并分叉核心逻辑。

需要补齐：

- 安装、升级、回滚和灾难恢复；
- SLO、监控、事件分级与医院通知；
- 安全测试、依赖清单和数据处理协议；
- 受控变更、回归验证和发布签署；
- 真实效率、安全、采用率和负面结果报告。

通过第二医院复制后，才有依据讨论正式版本、规模化销售或相邻功能扩展。

## 允许与禁止的产品扩展

只有同时满足以下条件，能力才可进入旗舰插件：

1. 服务同一用户：住院医生；
2. 发生在同一时点：查房前；
3. 使用同一患者上下文；
4. 改善同一指标：安全预阅效率；
5. 不引入新的诊断、治疗或监管主张。

可以纵向演进的方向：

- 更可靠的跨来源时间线与版本对齐；
- 检验、医嘱、报告之间的状态一致性检查；
- 医生可配置但有边界的视图排序；
- 经医生确认的病程草稿与来源保留；
- 安全的科室配置包和跨医院适配器。

不应加入同一旗舰的方向：

- 处方合理性裁决；
- 医保编码与结算；
- 临床试验招募；
- 自主诊疗建议；
- 医生画像、绩效管理或培训平台；
- 多 Agent 自主编排和在线自学习。

这些方向如需发展，应成为独立插件、独立预期用途和独立证据计划。

## 贡献原则

欢迎住院医生、临床信息科、医学信息学研究者、人因工程师和软件工程师参与。贡献应优先解决真实查房预阅摩擦，并同时提供：

- 明确的用户与触发时点；
- 可重现测试或真实验证方案；
- 数据来源与失败行为；
- 安全边界和回滚方式；
- 不支持情形与负面结果。

项目当前最需要的不是更多功能，而是首个真实病区的只读接入、连续病例证据和医生效率验证。
